# 문제 해결 기록

실제로 겪은 문제를 문제, 원인, 해결, 배운 점 순서로 남긴다.

## 마이그레이션 downgrade가 "Cannot drop index ... needed in a foreign key constraint"로 실패 (3단계)

**문제**: 첫 마이그레이션(테이블 5개 생성)을 개발 DB에 올린 뒤 `alembic downgrade base`로 왕복을 확인하자 종료 코드 1이 나왔다.
`alembic current`는 여전히 head였다.

```
pymysql.err.OperationalError: (1553, "Cannot drop index 'ix_idempotency_keys_group_id_entry_id':
needed in a foreign key constraint")
```

**원인**: downgrade가 autogenerate의 모양을 따라 `drop_index`를 하고 나서 `drop_table`을 했다.
`ix_idempotency_keys_group_id_entry_id`는 복합 외래 키 `(group_id, entry_id) -> journal_entries`가 쓰는 인덱스다.
InnoDB는 외래 키에 쓸 인덱스가 반드시 있어야 하므로, 테이블이 남아 있는 동안 그 인덱스만 지우는 것을 거부한다.
(기본키 앞부분이 외래 키 열과 같으면 기본키가 인덱스 역할을 하지만, 이 테이블의 기본키는 `(group_id, idem_key)`라 따로 인덱스가 필요했다.)

**확인**: MySQL DDL은 트랜잭션으로 되돌릴 수 없어서, 실패하면 반쯤 적용된 상태가 남을 수 있다(smart-elevator에서 겪은 문제).
`alembic current`와 실제 테이블, 인덱스를 먼저 확인했다. 첫 문장에서 실패했기 때문에 지워진 것은 없었다.

**해결**: downgrade에서 `drop_index`를 빼고 `drop_table`만 한다. 테이블을 지우면 그 테이블의 인덱스도 함께 지워진다.
고친 뒤 개발 DB에서 head -> base -> head 왕복과 `alembic check`를 다시 확인했다. 테스트도 세션마다 base -> head로 왕복한다.

**배운 점**
- 외래 키 열에 직접 만든 인덱스는 외래 키와 묶여 있다. 지우려면 외래 키를 먼저 지우거나 테이블째 지운다.
- 테스트 DB가 처음 비어 있을 때는 downgrade가 할 일이 없어 이 오류가 드러나지 않는다. 테이블이 있는 개발 DB에서 직접 왕복해 봐야 했다.

## 균등 분할의 남는 1원이 늘 같은 사람에게 간다 (3단계)

**문제**: API 테스트에서 민수가 10,000원을 내고 3명이 나누면 민수 잔액이 +6,667일 것이라고 적었는데, 실제로는 +6,666이었다.

**원인**: 남는 1원은 최대 나머지 방식으로 나누고, 나머지가 같으면 멤버 ID 순서로 준다(결정성, 1단계 설계).
균등 분할은 모두 나머지가 같으므로 **ID가 가장 앞선 멤버**가 3,334원을 낸다. 민수는 가장 먼저 등록돼 ID가 가장 작았다.
테스트를 쓰면서 "결제한 사람이 남는 돈을 덜 낼 것"이라고 막연히 생각했다.

**해결**: 테스트 기대값을 규칙대로 고쳤다(민수가 3,334원 부담, 잔액 +6,666). USD 테스트의 1센트도 같은 이유였다.

**배운 점 / 남은 문제**
- 규칙은 결정적이지만, 지출이 쌓이면 같은 사람이 매번 1원씩 더 낸다. 금액은 작아도 "늘 같은 사람"이라는 편향이다.
- 개선 후보: 남는 단위를 받을 순서를 분개 id로 돌리기(라운드 로빈), 또는 지금까지 남는 단위를 덜 받은 사람부터 주기.
  어느 쪽이든 결정성은 유지된다.
- **5단계에서 해결**: 출발점을 분개 순번(seq)만큼 돌린다. 균등 분할을 n번 하면 모두 같은 횟수만큼 낸다(property 테스트).

## PowerShell로 API를 부르면 한글이 `??`로 저장되거나 깨져 보인다 (3단계)

**문제**: README 사용 예를 Windows PowerShell 5.1의 `Invoke-RestMethod`로 실행했더니
첫 멤버 "민수"가 `??`로 저장됐고, 두 번째 "지영"도 `??`가 되어 이름 중복(409)이 났다.
`charset=utf-8`을 붙인 뒤에는 저장은 됐지만 응답의 이름이 `ë¯¼ì` 같은 글자로 보였다.

**원인**: 문제가 두 개 겹쳐 있었다. DB에 저장된 바이트를 직접 확인해 나눴다.
1. **요청**: `-ContentType "application/json"`처럼 charset이 없으면 PowerShell 5.1은 문자열 본문을
   ISO-8859-1로 인코딩한다. 한글은 이 문자 집합에 없으므로 `?`(0x3F)가 된다. DB에는 `3f3f`가 들어 있었다.
2. **응답**: 서버는 UTF-8로 보냈지만(`ebafbcec8898` = "민수") Content-Type이 charset 없는 `application/json`이었다.
   JSON은 표준(RFC 8259)상 UTF-8뿐이라 Starlette는 charset을 붙이지 않는데, PowerShell 5.1은 charset이 없으면
   ISO-8859-1로 읽는다.

**해결**
- 요청: README 예시의 모든 요청에 `-ContentType "application/json; charset=utf-8"`.
- 응답: 미들웨어(`app/main.py`의 `json_charset_utf8`)가 `application/json`에 `; charset=utf-8`을 붙인다.
  응답 클래스를 바꾸는 방법도 있지만, 그러면 FastAPI가 만드는 오류 응답(422 검증 오류, 401, 404)에는 적용되지 않아 미들웨어로 했다.
  테스트(`test_json_responses_declare_utf8`)가 성공 응답과 오류 응답 모두 확인한다.

**배운 점**
- 한글이 깨지면 "어디서" 깨졌는지 저장된 바이트(hex)로 먼저 나눈다. 보낼 때 깨진 것(`3f`)과 읽을 때 깨진 것(올바른 UTF-8을 잘못 해석)은 고치는 곳이 다르다.
- 표준상 필요 없는 값이라도 널리 쓰이는 클라이언트가 그 값에 기대면 붙이는 것이 실용적이다. charset을 붙여도 다른 클라이언트에는 해가 없다.
- TestClient(httpx)는 UTF-8로 주고받으므로 테스트로는 드러나지 않았다. README 예시를 실제 서버에서 그대로 실행해 보고 알았다.

## DB 테스트가 17초에서 70 ~ 100초로 느려졌다 (3단계)

**문제**: 테스트 수는 거의 같은데 전체 실행이 17초에서 70 ~ 100초가 됐다. `--durations`를 보면 모든 DB 테스트의 setup이 1.6 ~ 3.7초였다.

**원인**: 테스트마다 테이블 5개를 `TRUNCATE`로 비우고 있었다. InnoDB의 TRUNCATE는 행을 지우는 것이 아니라 테이블 파일(.ibd)을 지우고 새로 만든다(DDL).
파일 작업이라 디스크 상황(백신 검사 등)에 따라 느려진다. 빈 테이블 5개에 약 1.1초가 걸렸다. 처음에 빨랐던 이유는 확실히 알지 못한다.

| 방법 | 빈 테이블 5개 정리 |
| --- | --- |
| `TRUNCATE TABLE` | 1,004 ~ 1,259ms |
| `DELETE FROM` | 2 ~ 5ms |

**해결**: 정리를 `DELETE FROM`으로 바꿨다(외래 키 검사는 그 연결에서만 잠시 끈다). 전체 테스트는 13 ~ 20초로 돌아왔다.
DELETE는 AUTO_INCREMENT를 되돌리지 않으므로, "없는 분개 id"로 999 같은 작은 값을 쓰던 테스트는 절대 생길 수 없는 큰 값(10^15)으로 바꿨다.

**배운 점**
- 행이 몇 개 없는 테이블은 DELETE가 훨씬 싸다. TRUNCATE는 큰 테이블을 통째로 비울 때 유리하다(행마다 언두 로그를 남기지 않는다).
- 테스트가 느려지면 `--durations`로 call과 setup 중 어디가 느린지부터 본다.

## autogenerate가 만든 downgrade가 같은 1553 오류를 다시 만든다 (4단계)

**문제**: 정산 확정 테이블을 `alembic revision --autogenerate`로 만들었더니, downgrade가 다시 `drop_index` 두 개 다음 `drop_table` 순서였다.
3단계에서 겪은 "외래 키가 쓰는 인덱스는 먼저 지울 수 없다"(오류 1553)와 같은 모양이다.

**원인**: autogenerate는 인덱스와 테이블을 따로 비교해 "인덱스 삭제 -> 테이블 삭제"를 기계적으로 만든다. 그 인덱스가 외래 키에 묶여 있는지는 보지 않는다.

**해결**: 생성 파일을 읽고 downgrade를 `drop_table`만 남기도록 고쳤다. 개발 DB에서 upgrade -> downgrade -> upgrade 왕복과 `alembic check`를 확인했다.

**배운 점**: autogenerate 결과는 초안이다. CHECK 제약(변경을 못 잡음)과 외래 키 인덱스의 downgrade 순서는 매번 직접 읽는다. CLAUDE.md의 스키마 변경 절차에 넣었다. (6단계의 감사 로그 테이블에서도 같은 순서가 또 생성돼 고쳤다)

## 그룹 잠금을 넣자 "같은 키 동시 요청" 테스트가 장벽에서 멈췄다 (4단계)

**문제**: 분개 쓰기에 그룹 행 잠금을 넣은 뒤 `test_concurrent_requests_with_same_key_create_one_entry`가 `BrokenBarrierError`로 실패했다.

**원인**: 3단계의 테스트는 "네 요청이 모두 분개를 만드는 단계(`build`)에 동시에 들어와 장벽에서 만난다"는 실행 순서를 전제했다.
이제 `build`는 그룹 잠금 안에서 불리므로 한 번에 한 요청만 들어간다. 장벽은 네 명을 기다리다 시간 초과로 깨졌다.
잠금이 의도대로 동작해서 생긴 실패다.

**해결**: 테스트가 확인하려던 것("동시에 와도 분개는 하나")은 그대로 두고 실행 순서 전제를 바꿨다.
네 요청을 장벽에서 함께 출발시키고(잠금 없는 빠른 확인을 모두 통과), 처음 잠금을 잡은 요청이 `build` 안에서 0.3초 머물게 했다.
나머지는 잠금에서 기다렸다가 잠금 안의 재확인에서 먼저 커밋된 키를 보고 처음 결과를 돌려받는다. `build`가 한 번만 불렸는지도 확인한다.

**배운 점**: 동시성 테스트는 특정 실행 순서를 강제하는 장치(장벽, 이벤트)를 쓴다. 잠금 구조가 바뀌면 그 장치를 어디에 둘지 다시 정해야 한다. 실패가 "버그"인지 "전제가 바뀐 것"인지 먼저 구분한다.

## 스트레스 테스트에서 정산 확정이 한 번도 성공하지 못했다 (4단계)

**문제**: 스레드 8개가 지출, 송금, 취소, 확정을 섞어 보내는 테스트에서 확정이 31번 시도해 31번 모두 409(StaleVersionError)였다. 작업 사이에 0 ~ 5ms 간격을 넣어도 다섯 번 중 네 번은 0번 성공이었다.

**원인**: 확정은 "버전을 읽고 -> 그룹 잠금을 얻고 -> 버전 비교"다. 쓰기 스레드들이 그룹 잠금을 쉴 새 없이 잡고 있으면, 버전을 읽은 뒤 잠금 대기열에 서는 사이 앞에 늘 다른 쓰기가 있다. 그 쓰기가 커밋하면 버전이 바뀌어 있다.
낙관적 확인(읽은 버전이 그대로일 때만 성공)이 쓰기 경쟁 아래에서 굶는(starvation) 전형적인 모양이다.

**해결**
- 테스트: 쓰기 스레드와 확정 스레드를 나눴다. 확정 스레드는 쓰기가 도는 동안 계속 시도하고(대부분 409), 쓰기가 끝난 뒤 한 번 더 확정한다. 그래서 확정이 최소 하나 있는 상태에서 "모든 확정 계획 = 그 버전까지의 분개로 다시 계산한 계획"을 검사할 수 있다.
- 제품: 쓰기 간격에 따른 확정 성공률을 실험으로 쟀다([experiments.md](experiments.md)). 사람이 입력하는 모임은 쓰기 사이가 초 단위라 그대로 두고, 한계로 설계 문서에 적었다.

**배운 점**: 낙관적 동시성 제어는 충돌이 드물 때 좋다. 충돌이 잦으면 재시도가 끝나지 않는다. "보통 얼마나 자주 부딪히나"를 숫자로 확인하고 고른다.

## autogenerate가 통화 CHECK 변경과 새 CHECK를 전부 놓쳤다 (5단계)

**문제**: 지원 통화를 4개에서 9개로 늘리고 외화 증빙 열과 CHECK 5개를 `tables.py`에 추가한 뒤 `alembic revision --autogenerate`를 돌렸다.
생성된 마이그레이션에는 열 3개만 있었다. 그런데도 `alembic check`는 "차이 없음"이었다.
이대로 올리면 DB에는 옛 통화 CHECK가 남아, 새 통화(예: KWD)로 그룹을 만들 때 실제 사용자 요청이 500으로 실패한다.

**원인**: Alembic은 이미 있는 테이블의 CHECK 제약 내용을 비교하지 않는다(새 테이블을 만들 때만 그대로 옮긴다). CHECK 식을 DB마다 다른 모양으로 저장하기 때문이다.
MySQL은 `currency IN ('EUR', ...)`를 ``(`currency` in (_utf8mb4'EUR',...))``처럼 바꿔 저장한다.

**해결**
- 마이그레이션을 직접 썼다: 통화 CHECK는 지우고 새 목록으로 다시 만들고, 새 CHECK 5개를 추가했다. 통화 목록은 앱 상수를 import하지 않고 파일에 적었다.
- 같은 실수를 다시 잡을 장치: `test_db_currency_checks_match_app_currencies`가 `information_schema.CHECK_CONSTRAINTS`에서 DB의 CHECK 식을 읽어, 들어 있는 통화 코드가 앱의 `CURRENCIES`와 같은지 비교한다.

**배운 점**: `alembic check`가 통과해도 CHECK는 보장되지 않는다. 앱 상수에서 만들어지는 CHECK(통화, 종류, 방향)는 DB의 실제 식과 비교하는 테스트로 지킨다.

## 남는 1원을 받는 사람을 테스트에 이름으로 적었다 (5단계)

**문제**: 남는 단위의 출발점을 분개 순번만큼 돌리자, "민수가 3,334원을 낸다"고 적은 API 테스트 두 개가 실패했다. 순번 1인 첫 지출은 이제 ID 순서의 두 번째 사람이 낸다. 예상한 실패였지만, 고치다 보니 더 근본적인 문제가 보였다.

**원인**: 코어의 멤버 ID는 DB id를 **문자열로** 바꾼 값이고, 동점 순서는 문자열 정렬이다. 테스트는 "먼저 만든 멤버 = ID 순서가 앞"이라고 가정했다.
그런데 테스트 DB는 정리할 때 DELETE를 써서 AUTO_INCREMENT가 계속 늘어난다. id가 99, 100, 101이 되면 문자열 순서는 "100" < "101" < "99"라 먼저 만든 멤버가 맨 뒤로 간다. 언젠가 테스트 수가 늘면 순서와 상관없는 이유로 실패했을 것이다.

**해결**: 테스트에서 이름을 적지 않고 규칙으로 계산한다(`leftover_taker`: ID를 문자열로 정렬한 순서에서 순번째 멤버). 또 "지출 3번이면 세 사람이 한 번씩 낸다"처럼 순서와 무관한 성질을 확인하는 테스트를 더했다.

**배운 점**: 결정적인 규칙이라도 테스트가 규칙의 "결과"를 하드코딩하면, 입력(여기서는 id 값)이 바뀔 때 깨진다. 규칙 자체나 순서와 무관한 성질을 검사한다.

## 같은 리포트 쿼리가 21ms와 600ms를 오갔다 (6단계)

**문제**: 멤버별 요약 리포트를 줄 1만 개 그룹으로 재 봤더니, 같은 데이터인데 실행할 때마다 21ms와 600ms 사이를 오갔다. 앱에서 잴 때는 600ms, `EXPLAIN ANALYZE`로는 21ms가 나오기도 했다.

**원인**: 쿼리는 "멤버 LEFT JOIN (취소를 원래 종류로 바꾼 줄) → 멤버별 GROUP BY" 모양이었다. `EXPLAIN ANALYZE`를 느린 경우와 빠른 경우로 나눠 비교하니 계획이 달랐다.

| | 빠른 계획 (21ms) | 느린 계획 (600ms) |
| --- | --- | --- |
| 멤버마다 | 커버링 인덱스 `(group_id, member_id, ...)`로 **그 멤버의 줄만** 찾음 | **그룹의 분개 2,500개 전부**를 훑고 줄을 찾은 뒤 멤버로 거름 |
| 반복 | 줄 500개 x 20명 | 분개 2,500개 x 20명 = 5만 번 (`loops=20`, `loops=50000`) |

두 계획의 비용 추정이 비슷해서, 통계(ANALYZE 결과)가 조금만 달라도 옵티마이저가 다른 쪽을 골랐다.

**해결**: 쿼리 모양을 바꿔 느린 계획이 나올 수 없게 했다. 줄을 **멤버별로 먼저 집계**하는 CTE(`per_member`)를 만들고, 그 결과(멤버 수만큼의 행)를 멤버 목록에 LEFT JOIN한다.
이제 줄은 한 번만 읽힌다(`loops`가 줄 수 그대로). 줄 1만 개에서 75ms로 안정됐고, 결과는 이전 쿼리와 같았다(테스트로 비교).
인덱스 힌트(`FORCE INDEX`)로 계획을 고정하는 방법도 있지만, 데이터가 바뀌면 오히려 나쁜 계획을 강제할 수 있어 쓰지 않았다.

**배운 점**
- 한 번 잰 숫자는 믿지 않는다. 여러 번, 데이터를 다시 만들어 가며 재야 계획이 흔들리는 것이 보인다.
- `EXPLAIN`(추정)이 아니라 `EXPLAIN ANALYZE`(실제 실행)의 `loops`와 `actual time`을 본다.
- 집계 쿼리는 "먼저 줄이고(GROUP BY) 나중에 붙인다(JOIN)"가 대체로 안전하다.

## 데모 페이지에서 나중에 추가한 멤버가 지출 분담에서 빠졌다 (6단계)

**문제**: 데모 페이지에서 멤버를 한 명씩 추가한 뒤 지출을 기록했더니, 3명이 나눠야 할 30,000원이 결제자 혼자 부담으로 기록됐다. 브라우저로 직접 눌러 보며 확인하다가 발견했다(API 테스트로는 드러나지 않는 화면 버그).

**원인**: "나눌 사람" 체크박스를 다시 그릴 때 "이전에 체크돼 있던 사람"을 기억해 그대로 체크했다. 첫 멤버만 있을 때 그 멤버가 체크된 상태가 기억되고, 이후 추가된 멤버는 그 목록에 없어서 체크가 빠진 채로 나타났다.

**해결**: "체크된 사람" 대신 **"사용자가 뺀 사람"**을 기억한다. 새 멤버는 기본으로 포함된다. 잘못 기록된 지출은 취소(역분개)하고 다시 기록했다. 원장은 그 이력을 그대로 보여 준다(취소된 줄은 흐리게).

**배운 점**: 기본값이 "포함"인 선택은 "제외 목록"으로 기억해야 새 항목이 자연스럽게 포함된다. 그리고 화면은 직접 눌러 봐야 한다.

## 로컬 서버에서 X-Forwarded-For 위조로 빈도 제한이 풀렸다 (배포 준비)

**문제**: 배포 준비로 빈도 제한(그룹 만들기 시간당 10번)을 넣고 로컬 서버에서 확인했다. 11번째 요청은 429였지만, 같은 요청에 `X-Forwarded-For: 9.9.9.9`를 붙이자 201로 통과했다. 테스트(`test_spoofed_forwarded_for_does_not_bypass_the_limit`)는 통과하고 있었다.

**원인**: uvicorn의 기본값이다. `proxy_headers=True`, `forwarded_allow_ips=127.0.0.1`이라, **127.0.0.1에서 온 요청은 `X-Forwarded-For`를 믿고 `request.client.host`를 그 값으로 바꿔 넣는다.** 로컬에서 curl로 보낸 요청은 127.0.0.1에서 오므로 위조한 값이 그대로 접속자 IP가 됐다. 앱의 `client_ip`는 이미 바뀐 값을 받았다.
테스트는 TestClient로 돌아 uvicorn을 거치지 않아서 이 문제가 드러나지 않았다.

**해결**: uvicorn을 `--no-proxy-headers`로 띄우고, IP 해석은 앱이 `TRUSTED_PROXY_HOPS`로만 한다. `render.yaml`과 CI 스모크 테스트는 이미 이 옵션을 쓰고 있었고, 로컬 실행 설정과 README·CLAUDE.md의 실행 명령에도 넣었다. 다시 확인하니 위조한 헤더 세 가지 모두 429였다.

**배운 점**
- 앱 코드가 맞아도 앞단(서버 프로세스, 프록시)의 기본값이 입력을 바꿔 놓을 수 있다. 보안 기능은 실제 서버로 한 번 더 확인한다.
- 같은 서버 안에 리버스 프록시(nginx 등)를 두는 구성이면 127.0.0.1을 믿는 기본값이 맞을 수도 있다. "누가 이 헤더를 붙이는가"를 구성마다 정하고 그 수만큼만 믿는다.
