# 실험

## 2단계: 그리디 vs 최적 정산

질문: 그리디(가장 많이 받을 사람 ↔ 가장 많이 낼 사람)로 충분한가, 최적 계산이 필요한가?

재현: `.\.venv\Scripts\python.exe -m scripts.compare_settlement` (seed 42, 모임마다 300번)

환경: Windows 11 로컬 PC, Python 3.11. 시간은 기계마다 다르므로 비율과 증가 추세만 본다.

### 방법

n명 모임에서 지출 3n건을 무작위로 만들어 실제로 원장(`Ledger`)에 기록하고, 그 잔액으로 두 방법을 돌린다.

- **realistic**: 금액이 500원 단위(500 ~ 200,000원), 참여자는 2명 ~ 전원
- **round**: 금액이 10,000원 단위(10,000 ~ 50,000원), 참여자 2 ~ 3명. "만 원씩 나눠 낸" 모임처럼 잔액이 같은 값으로 겹치기 쉽다

k = 잔액이 0이 아닌 사람 수. 어떤 방법이든 송금은 k - 1번을 넘지 않는다.

### 해석

- **금액이 제각각이면 그리디도 최적이다.** 최적이 그리디보다 나으려면 "합이 정확히 0인 작은 묶음"이 있어야 하는데,
  500원 단위의 다양한 금액에서는 그런 묶음이 거의 생기지 않는다. 이때 최적 = 그리디 = k - 1.
- **금액이 둥글면 차이가 커진다.** 만 원 단위로 몇 명씩 나눈 모임은 잔액이 같은 값(예: +10,000과 -10,000)으로
  겹쳐 묶음이 잘 생긴다. 12명이면 64%의 모임에서 그리디가 1 ~ 2번 더 보낸다. 실제 모임은 이쪽에 가깝다
  (회비, 1/N 정액).
- **시간은 2^k로 늘어난다.** k가 2 늘 때마다 약 4.5배. 16명 37ms, 20명 870ms.
  인원이 늘수록 최적의 이득도 커지지만 시간이 감당할 수 없게 늘어난다.

### 결정

- 기본은 `Strategy.AUTO`: 잔액이 남은 사람이 **16명 이하면 최적, 넘으면 그리디**.
  16명에서 수십 ms라 API 요청 안에서 계산해도 된다. 서버가 느리더라도(무료 인스턴스) 여유가 있다.
- 한도(`DEFAULT_OPTIMAL_LIMIT`)는 설정으로 바꿀 수 있게 3단계에서 연결한다.
- 그 이상 인원에서 더 줄이고 싶다면: 크기 2인 묶음(+x와 -x)을 먼저 짝짓는 휴리스틱, 또는 메모이제이션 DFS
  같은 방법이 있다. 정산 모임은 대부분 16명 이하이므로 지금은 하지 않는다.
