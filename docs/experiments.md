# 실험

## 2단계: 그리디 vs 최적 정산

질문: 그리디(가장 많이 받을 사람 ↔ 가장 많이 낼 사람)로 충분한가, 최적 계산이 필요한가?

재현: `.\.venv\Scripts\python.exe -m scripts.compare_settlement` (seed 42, 모임마다 300번)

환경: Windows 11 로컬 PC, Python 3.11. 시간은 기계마다 다르므로 비율과 증가 추세만 본다.

### 방법

n명 모임에서 지출 3n건을 무작위로 만들어 실제로 원장(`Ledger`)에 기록하고, 그 잔액으로 두 방법을 돌린다.

- **realistic**: 금액이 500원 단위(500 ~ 200,000원), 참여자는 2명 ~ 전원
- **round**: 금액이 10,000원 단위(10,000 ~ 50,000원), 참여자 2 ~ 3명. "만 원씩 나눠 낸" 모임처럼 잔액이 같은 값으로 겹치기 쉽다

k = 잔액이 0이 아닌 사람 수. 어떤 방법이든 송금은 k - 1번을 넘지 않는다.

### 최적 DP 실행 시간

| k (잔액이 남은 사람) | 2^k x k | 최적 ms | 그리디 ms |
| ---: | ---: | ---: | ---: |
| 8 | 2,048 | 0.1 | 0.017 |
| 10 | 10,240 | 0.4 | 0.022 |

| 14 | 229,376 | 8.2 | 0.033 |
| 16 | 1,048,576 | 36.6 | 0.044 |

| 20 | 20,971,520 | 867.8 | 0.055 |

### 해석

- **금액이 제각각이면 그리디도 최적이다.** 최적이 그리디보다 나으려면 "합이 정확히 0인 작은 묶음"이 있어야 하는데,
  500원 단위의 다양한 금액에서는 그런 묶음이 거의 생기지 않는다. 이때 최적 = 그리디 = k - 1.
- **금액이 둥글면 차이가 커진다.** 만 원 단위로 몇 명씩 나눈 모임은 잔액이 같은 값(예: +10,000과 -10,000)으로
  겹쳐 묶음이 잘 생긴다. 12명이면 64%의 모임에서 그리디가 1 ~ 2번 더 보낸다. 실제 모임은 이쪽에 가깝다
  (회비, 1/N 정액).
- **시간은 2^k로 늘어난다.** k가 2 늘 때마다 약 4.5배. 16명 37ms, 20명 870ms.
  인원이 늘수록 최적의 이득도 커지지만 시간이 감당할 수 없게 늘어난다.

### 결정

- 기본은 `Strategy.AUTO`: 잔액이 남은 사람이 **16명 이하면 최적, 넘으면 그리디**.
  16명에서 수십 ms라 API 요청 안에서 계산해도 된다. 서버가 느리더라도(무료 인스턴스) 여유가 있다.
- 한도(`DEFAULT_OPTIMAL_LIMIT`)는 설정으로 바꿀 수 있게 3단계에서 연결한다.
- 그 이상 인원에서 더 줄이고 싶다면: 크기 2인 묶음(+x와 -x)을 먼저 짝짓는 휴리스틱, 또는 메모이제이션 DFS
  같은 방법이 있다. 정산 모임은 대부분 16명 이하이므로 지금은 하지 않는다.

## 4단계: 잔액 계산 방식과 동시성

실행: `.\.venv\Scripts\python.exe -m scripts.compare_balances` (테스트 DB를 비우고 쓴다). 로컬 Windows 11, MySQL 8.0, 멤버 20명, 분개마다 줄 4개.
조회는 다른 그룹의 줄 10만 개를 섞어 둔 테이블에서 잰다(한 그룹만 있으면 인덱스 효과가 과장된다). 시간은 30회 중앙값이고, 연결 풀에서 연결을 꺼내는 시간과 `Money` 변환까지 포함한 앱 기준이다.

### 1) 잔액 조회

| 그룹의 줄 수 | SUM (ms) | SUM + 커버링 인덱스 (ms) | 잔액 테이블 (ms) | SUM이 쓴 인덱스 | 커버링일 때 |
| ---: | ---: | ---: | ---: | --- | --- |
| 1,000 | 10.84 | 11.65 | 0.64 | PRIMARY (Using where) | PRIMARY (Using where) |

| 1,000,000 | 5494.07 | 711.06 | 1.27 | ix_entry_lines_group_id_member_id (-) | ix_bench_cover (Using index) |

### 2) 분개 기록

| 방식 | 분개 하나 기록 (ms, 중앙값) |
| --- | ---: |
| 원장만 (지금) | 8.17 |

(참고: 잔액 테이블 없이 기록한 201건 때문에 어긋난 멤버 수 20. 두 저장소를 함께 쓰면 모든 쓰기 경로가 둘 다 갱신해야 한다)

### 3) 잔액 테이블의 동시 갱신

스레드 8개 x 송금 200건, 멤버 4명 (그룹 잠금 없음)

| 방식 | 데드락 (재시도) | 기대값과의 차이 합 | 잔액 합 | 시간 (s) |
| --- | ---: | ---: | ---: | ---: |
| 읽고 더해서 쓰기 (SELECT 후 UPDATE) | 320 | 64,918 | -44,634 | 5.17 |
| UPDATE balance = balance + ?, 순서 없음 | 279 | 0 | 0 | 4.14 |
| UPDATE balance = balance + ?, 멤버 id 순서 | 0 | 0 | 0 | 3.66 |

### 4) 정산 확정 성공률

쓰기 스레드 4개가 3초 동안 송금을 기록하는 사이, 확정 스레드 하나가 계속 시도

| 쓰기 사이 간격 | 기록된 분개 | 확정 시도 | 성공 | 성공률 |
| ---: | ---: | ---: | ---: | ---: |
| 0ms | 234 | 58 | 0 | 0% |
| 2ms | 223 | 73 | 0 | 0% |
| 10ms | 228 | 76 | 0 | 0% |
| 50ms | 180 | 228 | 100 | 44% |

### 해석

- **조회: 커버링 인덱스가 3 ~ 8배 빠르다.** 지금 인덱스 `(group_id, member_id)`는 줄을 찾은 뒤 `side`, `amount`를 읽으러 기본키(클러스터형 인덱스)로 다시 간다. 줄 하나마다 임의 접근이 한 번씩 더 생긴다. `(group_id, member_id, side, amount)`는 인덱스만 읽는다(`Using index`). 줄 1만 개 25ms -> 7ms, 100만 개 5.5초 -> 0.7초.
- 줄이 1천 개일 때는 옵티마이저가 두 경우 모두 기본키 앞부분(`group_id`)을 훑었다. 이 크기에서는 차이가 없고 고정 비용이 대부분이다.
- **잔액 테이블은 크기와 상관없이 1ms 안팎이다.** 대신 쓰기마다 멤버 행 UPDATE가 붙어 기록이 약 1.7ms(20%) 느려지고, 원장과 잔액 테이블이 어긋나지 않게 모든 쓰기 경로가 둘 다 갱신해야 한다(실험에서 잔액 테이블을 건너뛴 기록 201건 때문에 20명 모두 어긋났다).
- **잔액 테이블의 동시 갱신은 함정이 두 개다.**
  - 읽고 더해서 쓰기: 다른 트랜잭션의 갱신을 덮어써 **잃어버린다.** 기대값과 64,918 차이, 잔액 합이 0이 아니라 -44,634. 이중기입의 "합은 항상 0"이 깨진다.
  - `UPDATE balance = balance + ?`는 값은 맞지만, 송금마다 멤버 두 명을 서로 다른 순서로 잠그면 **데드락**이 279번 났다(MySQL이 한쪽을 롤백, 재시도로 해결).
  - 멤버 id 순서로 UPDATE하면 데드락 0. 잠금을 항상 같은 순서로 잡으면 순환 대기가 생기지 않는다.
- **정산 확정은 쓰기가 몰리면 굶는다.** 쓰기 4개가 10ms 간격 이하로 계속 기록하면 확정 성공 0%, 50ms 간격에서 44%(같은 조건의 짧은 실행에서는 82%, 기계 부하에 따라 흔들린다). 그룹 잠금이 거의 늘 잡혀 있으면, 버전을 읽은 뒤 잠금을 얻기 전에 다른 쓰기가 먼저 커밋한다.

### 결정

- **커버링 인덱스를 넣는다** (마이그레이션 `b37a5d0c1e92`). 기존 `(group_id, member_id)`를 대신하고 멤버 외래 키의 인덱스 역할도 한다. 실제 앱 쿼리의 `EXPLAIN`에서 `Using index`를 확인했다.
- **잔액 테이블은 넣지 않는다.** 여행 모임 하나는 분개 수백 개(줄 수천 개)이고, 오래 쓰는 모임도 줄 1만 개 안팎이다. 이 크기에서 커버링 인덱스 SUM은 10ms 안쪽이다. 원장 하나만 진실의 원천으로 두면 어긋날 일이 없다.
- 그룹 하나에 줄이 수십만 개 쌓이는 쓰임새(가계부처럼 몇 년 쓰는 그룹)가 생기면 다시 본다. 후보:
  - 잔액 테이블을 그룹 잠금 안에서 멤버 id 순서로 갱신 (이미 그룹 잠금을 잡으므로 같은 그룹 안의 갱신 손실과 데드락이 없다)
  - 체크포인트: "순번 N까지의 잔액"을 가끔 저장하고, 조회는 체크포인트 + N 이후 줄만 SUM. 원장이 여전히 원천이고 체크포인트는 다시 만들 수 있다.
- 확정 굶주림은 사람 입력 속도에서는 문제가 아니라 그대로 둔다 (docs/design.md 4단계 "알려진 한계").
